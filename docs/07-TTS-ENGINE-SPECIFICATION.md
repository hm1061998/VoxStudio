# 07 — TTS Engine Specification (Strict Non-AI)

> **Scope clarification (ADR 0007, 2026-10-31):** "non-AI" applies to **run time**. Audio generated by a locally run AI model during development may be used as source data for a recorded-unit voice if its provenance (generator, version, license, local run) is declared in the dataset manifest and disclosed in the UI. No model or AI runtime may be part of the application.

## 1. Compliance definition

Allowed:

- Deterministic rule-based grapheme-to-phoneme conversion.
- Rule-based letter-to-sound and phoneme rules.
- Formant synthesis.
- Deterministic concatenative synthesis using fixed, licensed recorded units.
- Conventional DSP.
  Not allowed:
- Neural TTS or neural vocoders.
- Statistical parametric speech synthesis or learned acoustic models.
- Machine-learning phoneme/acoustic prediction.
- LLM text-to-speech or text normalization.
- Voice cloning, speaker adaptation, or generative audio.
- External cloud TTS endpoints.

## 2. Initial engine candidate: eSpeak NG

Treat eSpeak NG as the initial candidate, not an automatic compliance or quality guarantee. Verify the exact release, synthesis method, voice definitions, dependencies, and license before approval. Build a compliance record and test each locale/voice.

Integration:

- Run as a pinned executable in the worker container.
- Use argument arrays and fixed executable path.
- Generate an intermediate WAV in a per-job temp directory.
- Capture stderr safely; redact user text if command output includes it.
- Validate output header, duration, sample rate, channels, and decodability.
- Enforce timeouts and output size limits.
- Clean temp files on success, failure, and cancellation.

## 3. Engine admission checklist

Before enabling any engine:

- [ ] Document synthesis method from authoritative upstream documentation/source.
- [ ] Confirm no statistical/ML/neural speech generation.
- [ ] Review all runtime dependencies.
- [ ] Review engine and voice-package licenses.
- [ ] Confirm redistribution and commercial use rights.
- [ ] Pin binary and voice package versions.
- [ ] Build locale-specific pronunciation test corpus.
- [ ] Test Unicode and punctuation behavior.
- [ ] Test parameter mappings and ranges.
- [ ] Add reproducible integration tests.
- [ ] Record approval, reviewer, date, and evidence.
      If method cannot be established, mark `unverified` and do not expose it.

## 4. Engine metadata

```ts
interface EngineMetadata {
  id: string;
  name: string;
  version: string;
  synthesisMethod: string;
  complianceStatus: 'approved' | 'unverified' | 'rejected';
  license: string;
  supportedLocales: string[];
}

interface VoiceMetadata {
  id: string;
  engineId: string;
  name: string;
  locale: string;
  accent?: string;
  packageVersion: string;
  license: string;
  qaStatus: 'untested' | 'testing' | 'passed' | 'failed';
}

interface ParameterCapability {
  support: 'native' | 'dsp' | 'unsupported';
  min?: number;
  max?: number;
  default?: number;
  step?: number;
  unit?: string;
  description?: string;
}
```

## 5. Locale and voice discovery

Do not infer support from locale names alone. Build an installed-voice manifest at startup and reconcile it against an allowlist. Only approved and QA-passed voices appear in normal user selection. Unverified voices may appear in admin diagnostics only.

## 6. Parameter mapping

- Speed: map to engine-native rate if supported; otherwise use DSP time-stretch only if explicitly selected.
- Pitch: map to native pitch if supported; otherwise DSP pitch shift.
- Volume: preferably post-synthesis gain with headroom protection.
- Pause: insert exact silence samples after synthesis.
- Emphasis/intonation: expose only if engine has deterministic support or a clearly labeled DSP approximation. Do not pretend ordinary gain changes create linguistic stress.
- Breath: do not synthesize fake breath noise by default. Optional user-supplied licensed sound assets may be placed on timeline, but this is a separate audio asset feature.

## 7. Text normalization

Implement deterministic locale-specific rules. Examples: numeric expansion, dates, currency, abbreviations, punctuation, URL handling. Preserve original text. Show normalized preview. Unknown patterns must not be expanded by an LLM or guessed silently.

## 8. Pronunciation

Support deterministic dictionary substitutions. Engine-specific phoneme syntax must be validated against that engine and locale. Keep source token, replacement/phoneme string, locale, engine scope, and priority. Avoid unsafe regex from user input; use literal matching by default.

## 9. Voice quality and coverage

For every locale/voice:

- Record tested sample corpus and version.
- Evaluate pronunciation, intelligibility, rhythm, accent, artifacts, and stability.
- Have native or qualified reviewers assess language-specific output where feasible.
- Display a support tier (verified / experimental / unavailable) with transparent notes.
  Never claim universal language coverage simply because the engine has a locale identifier.

## 10. Licensing

Maintain `THIRD_PARTY_NOTICES.md` and an inventory of engine, voice package, phoneme data, and binary licenses. Review commercial use, modification, redistribution, attribution, and copyleft obligations. Do not bundle a voice package until its license is approved.
